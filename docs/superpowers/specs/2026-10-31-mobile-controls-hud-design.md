## 1. Goals and boundaries (SDD)

Default immersive Hybrid A+B with opt-in Competitive C from Settings; adjustable safe-area thumb controls, NITRO READY/charging/active/disabled and compact notices. Both iPhone/Android portrait/landscape and desktop.

This branch's design is limited to the stated responsibilities. The separate source-of-truth requirements for the full project are in [the planning TODO](https://github.com/weskao/skyline-rush/blob/feature/ux-ui-combo-mobile-controls/TODO.md); do not confuse this branch's inherited older `TODO.md` with the newer planning file.

## 3. Behavior (BDD — acceptance scenarios)

#### Scenario 1: Default

**Given** HUD preference absent

**When** race is opened

**Then** Hybrid A+B displays essentials without central occlusion

#### Scenario 2: Competitive C

**Given** user chooses C in Settings

**When** they rotate/reload

**Then** fuller info displays with saved preference and safe control bounds

#### Scenario 3: READY

**Given** NITRO crosses actionable threshold

**When** subsequent frames render

**Then** one cue plays and persistent visible READY state remains

#### Scenario 4: Touch editing

**Given** player drags controls in edit mode

**When** they save layout

**Then** no ability fires, controls remain in safe areas, reset works

## 4. Interfaces, migration and non-goals

- The owning implementation plan must define the smallest typed contract across affected source modules and deterministic tests before code. No unbounded new dependencies, classes or parallel state stores.
- Do not alter gameplay/ownership/race records incidentally or allow visual Quality to change physics, HUD options, progress or owned inventory.
- Preserve preexisting iPhone/Android browser input, keyboard/mouse, interruption recovery and finish/pause clickability; all new player copy must be bilingual.
- The following are mandatory review risks, with tests assigned in the plan:
1. Topbar z-index and invisible overlays can intercept results/camera controls
2. Per-frame HUD must not use Vue reactive writes or repeated DOM queries
3. WebKit may miss pointerup/cancel on back swipe
4. READY must be based on actual usable charge not animation alone
5. Compact C must not obscure obstacles on narrow landscape
